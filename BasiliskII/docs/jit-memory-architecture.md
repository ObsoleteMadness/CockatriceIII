# JIT-First Memory & CPU Architecture

## 1. Current State: How BasiliskII Handles Memory Today

- **Flat host window, not a bank table.** `memory.cpp` reserves a single flat 4GB host mapping (`Host_Mem_Base`); a Mac address maps to a host pointer via `Mac2HostAddr` = `Host_Mem_Base + addr` (`include/cpu_emulation.h:150-156`). There is no per-region dispatch/bank array — UAE's classic `map_banks()` model has been collapsed away (see header comment, `memory.cpp:6-11`).
- **Two protection modes.** "Flat dummy window" (default): the whole 4GB is RW-committed, so unmapped holes silently behave like RAM — simplest and fastest for JIT direct-pointer access. "Strict holes": the 4GB is reserved `PROT_NONE`; only RAM/ROM/framebuffer ranges are `mprotect`'d RW (`memory_commit_range`, `memory.cpp:269`), and a host SIGSEGV/SIGBUS on an unmapped address is caught and converted into a 68k vector-2 (address/bus error) via a nested guard-stack (`memory_guard_enter/leave`, `memory_unix_fault`, `memory.cpp:511`).
- **Inline accessors, not raw dereference.** All callers go through `ReadMacInt8/16/32`/`WriteMacInt8/16/32` (`cpu_emulation.h:184-286`). Endian swap is inline per-platform (`do_get_mem_word/long` in each `sysdeps.h`; OSX64 uses `__builtin_bswap32/16` since Apple Silicon is little-endian but 68k is big-endian).
- **24-bit addressing** is a live toggle, `TwentyFourBitAddressing` (`cpu_emulation.h:59`), masking `addr &= 0x00ffffff` in `Mac2HostAddr` when set. It's derived from ROM generation in `main.cpp:79-101`: 64K/Plus/Classic/II ROMs → 24-bit; 32-bit-clean ROMs → false. There's no separate `DIRECT_ADDRESSING`/`REAL_ADDRESSING` compile switch left — direct addressing is the only mode now. **Going forward this collapses to a constant**: with classic-Mac support dropped, only 32-bit-clean ROMs are ever loaded, so `TwentyFourBitAddressing` is always `false` and the whole 24-bit code path becomes dead weight (see roadmap Phase 2).
- **MMU is never emulated for the guest.** BasiliskII patches the ROM to skip it: `rom_patches.cpp:1036-1074` NOPs three `InitMMU` routines, and `emul_op.cpp` zeroes a "no MMU present" flag. The flat window means every 68k logical address is already the host offset — there's no guest-visible translation to emulate. This is unaffected by (and consistent with) the "sans MMU" 68040 target — the ROM-patch approach already assumes no real MMU regardless of CPU model.
- **CPU model was going to matter for alignment-trap correctness — until the scope was narrowed.** The `"cpu"` prefs key (`prefs.cpp:57,104`) selects 0=68000 … 4=68040 (default already 68040). Real 68020+ hardware never raises an address error on unaligned word/long access — only 68000/68010 do. With classic (68000/68010/68020) support being dropped entirely and the machine fixed at 68040, this distinction stops being a runtime question: **the emulated machine can never legitimately need an unaligned-access trap**, so the pref's 0-3 values become dead code (see roadmap Phase 2).
- **Memory-mapped devices: only the SCC (serial) is true MMIO today, but that's a matter of what's been built, not an architectural ceiling.** `is_scc_addr()` (`cpu_emulation.h:117-138`) range-checks 24-bit and 32-bit SCC windows inline inside the hot accessor path, dispatching to `scc_bget/bput` → `SCC_Access()`. Every other device — SCSI, floppy/Sony, ADB, video, sound, Ethernet, PRAM/clock — is **not** memory-mapped at all; it's intercepted via 68k illegal-opcode traps (`EMUL_OP` values planted into patched ROM driver code, dispatched by `EmulOp()` in `emul_op.cpp`). SCC is special-cased directly in `ReadMacInt*`/`WriteMacInt*` rather than going through any generic MMIO mechanism — there's no registration point for a second device to become memory-mapped without hand-editing the same accessor functions again. As reliability/functionality work continues, more devices (VIA, ADB, possibly others) are plausible candidates to move from trap-based `EMUL_OP` interception to real MMIO, so the region model (§2A) needs to treat "MMIO with a handler" as a first-class, extensible region kind, not a hardcoded SCC special case.
- **CPU backend abstraction already exists and is runtime-selected.** `cpu_engine.cpp` defines a `CPUEngine` vtable registry (`RegisterCPUEngine`, up to 8 slots), currently holding 5 engines: Musashi, UAE/Amiberry (interpreter + "compemu" JIT), Emu68, syn68k, m68k-rs. Selection is the `"cpu_emulator"` prefs string (`main.cpp:104-111`), not a compile-time `#ifdef`. The test harness (`tests/cpu/cpu_test_main.cpp`, `tests/include/test_env.cpp`) can hot-swap engines within one process across `kTestEngineConfigs[]`.
- **Direct-pointer vs. callback memory access already varies by backend, ad hoc.** m68k-rs defaults to FFI callbacks (`read_byte/word/long`/`write_byte/word/long` wired straight to `ReadMacIntN`/`WriteMacIntN`, `m68k_rs_glue.cpp:171-204`) so it preserves SCC/ROM-protect/guard semantics; it also has an optional raw `fast_mem` pointer path, **disabled by default** after a documented past incident of silent SCSI corruption when it bypassed the SCC/ROM hooks. UAE's compemu JIT and Emu68, by contrast, inline `Host_Mem_Base`-relative pointer arithmetic directly into generated code for speed, relying on guard-page faulting for the rare bad access.
- **UAE's ARM64 JIT ("compemu") already implements 3 of the 4 JIT quirks correctly** (`amiberry/src/jit/arm/`):
  - *Unaligned access*: gated by `CPU_CAN_ACCESS_UNALIGNED`, which `OSX64/sysdeps.h:82-83` defines **unconditionally** for this build — meaning odd-address word/long accesses currently succeed silently instead of trapping. Initial research flagged this as a correctness gap (real 68000/68010 hardware traps here). **With the machine now fixed at 68040, it isn't a gap at all** — real 68040 hardware never traps on unaligned access either, so letting ARM64 hardware handle it natively is exactly correct. No alignment-check code needs to be added anywhere in the JIT.
  - *W^X*: correct and non-trivial — `pthread_jit_write_protect_np()` wrapped in a **thread-local** nesting counter (`jit_begin_write_window`/`jit_end_write_window`, `compemu_support_arm.cpp:772-811`), explicitly thread-local because a second thread can patch code (SMC) concurrently with block compilation on the main thread; a shared counter would race. `MAP_JIT` allocation at `compemu_support_arm.cpp:2769-2868`.
  - *I/D-cache coherency*: `flush_cpu_icache()` branches to `sys_icache_invalidate` (Apple) / `FlushInstructionCache` (Windows ARM64) / `__builtin___clear_cache` (else), called after every block compile and after every branch-target SMC patch (`compemu_midfunc_arm64.cpp:701-752`).
  - *Flags*: classic lazy-NZCV state machine (`needflags`/`live.flags_in_flags`/`live.flags_are_important`, `compemu_support_arm.cpp:822-846`) — flags are only materialized when a subsequent branch actually needs them.
- **m68k-rs has JIT ambitions too, but they're unverified on this platform.** `vendor/m68k-rs` has an optional Cranelift-based trace JIT (default-on feature). Whether Cranelift's own JIT memory manager correctly cooperates with macOS Hardened Runtime / `MAP_JIT` / `pthread_jit_write_protect_np`, or silently relies on assumptions that don't hold under the sandboxed/hardened build, was **not confirmed** by this research — flagged as an open risk below.
- **Emu68 and syn68k never reached a working state in this project** and are vendored dead weight: `Emu68/upstream` (submodule) + a bespoke `hosted/` port layer including its own `emu68_darwin_jit.h` W^X handling (a third, separate copy of the same JIT-host-support logic UAE already implements correctly); `syn68k/` is an ad hoc, untracked nested checkout.

## 2. Greenfield Target Architecture

The right design isn't a rewrite — it's formalizing what's already implicit, and removing duplication between backends. Five pieces:

**A. One address-map source of truth, with MMIO as a generic, extensible region kind.** A small sorted `MemoryRegion` table (kind: RAM / ROM / **MMIO** / Unmapped; host base; mac base; length) built once in `memory_init()`, replacing the hardcoded ranges currently duplicated between `is_scc_addr()` and m68k-rs's separately-populated `m68k_rs_set_mapped_ranges()`. Critically, `MMIO` regions carry a registered read/write handler (function pointer pair, or a small vtable) rather than being a single hardcoded "is this the SCC" branch — SCC becomes the first registered handler (`RegisterMMIORegion(base, length, scc_bget, scc_bput)`), not a special case baked into the accessor functions. This is the piece that matters for extensibility: adding a second memory-mapped device (VIA, ADB, or whatever reliability work motivates next) means registering a new region + handler, not re-editing `ReadMacInt8/16/32`/`WriteMacInt8/16/32` again. Every consumer — the slow-path accessors (now a generic "is this address in an MMIO region → call its handler" check instead of `is_scc_addr()`), any JIT backend deciding whether to inline a direct load vs. call the slow path, and each backend's bounds cache — reads this one table.

**B. Direct-pointer vs. callback as a declared per-engine capability, not a discovered fact.** Add an explicit `mem_strategy` field to `CPUEngine` (`DirectPointer` vs `Callback`). m68k-rs's existing (currently-disabled) `fast_mem` toggle becomes the reference example of a `Callback` engine opting into `DirectPointer` once its bounds-checking against the region table (A) is trusted — rather than a special case discovered by reading glue code.

**C. No alignment trapping at all — the fixed-68040 decision resolves this outright.** Real 68040 hardware never faults on unaligned word/long access, so there is no correctness case where the emulator needs to insert one. This removes what would otherwise have been the hardest item in the JIT quirk list (inlining alignment checks into codegen, plus the unresolved question of hooking m68k-rs's Cranelift lowering to inject one). The existing ARM64 behavior — `CPU_CAN_ACCESS_UNALIGNED` unconditionally on, letting the host CPU's native unaligned-access support do the work — is already the correct, final design for every backend. Nothing to build here; this section exists to record *why* it was considered and ruled out, so a future contributor doesn't reopen it thinking it's an oversight.

**D. One shared JIT-host-support module**, e.g. `BasiliskII/jit_support/{jit_host.h, jit_host_darwin.cpp, jit_host_win32.cpp}`, owning W^X toggling (promote the existing correct thread-local `pthread_jit_write_protect_np` pattern from `compemu_support_arm.cpp` — don't reinvent it), icache/dcache flush, and JIT-buffer allocation. Both surviving JIT backends (UAE compemu, m68k-rs/Cranelift) call into it instead of each owning a private copy. This also gives the Cranelift integration a known-correct place to plug in rather than trusting `cranelift-jit`'s own memory manager to guess right under Hardened Runtime.

**E. `CPUEngine` capability flags.** Extend the struct with `mem_strategy` (from B) and a `tier` (`golden` vs `performance`) so the test harness and any future prefs UI encode the Musashi-is-truth / others-are-tradeoffs policy explicitly in code instead of by convention.

## 3. Gap-Closing Roadmap

**Phase 0 — Retire dead backends** (low risk, unblocks everything else). Remove Emu68 (submodule + `BasiliskII/Emu68/*`) and syn68k (`BasiliskII/syn68k/*`) from `cpu_engine.cpp`'s registry, build files, `.gitmodules`, and `kTestEngineConfigs`. Immediately drops JIT-plumbing duplication from 3 copies to 2.

**Phase 1 — Unify the address map with a generic MMIO registration point.** Introduce the `MemoryRegion` table (A) in `memory_init()`, including the MMIO-with-handler mechanism; migrate SCC to be its first registered handler instead of a hardcoded branch in `ReadMacInt*`/`WriteMacInt*`; point `m68k_rs_set_mapped_ranges()` at the same table. Touches `cpu_emulation.h`, `memory.cpp`, `m68k_rs_glue.cpp`. This is the phase that pays off directly the next time a device (VIA, ADB, etc.) moves from `EMUL_OP` trap interception to real MMIO — it becomes a registration call instead of another hand-edited accessor branch.

**Phase 2 — Strip classic-Mac dead weight now that the target is fixed at 68040.** Hardcode the `"cpu"` pref to 68040 (or remove the pref's other values entirely) in `prefs.cpp`; delete the 64K/Plus/Classic/II ROM-version branches in `main.cpp:79-101` that set `TwentyFourBitAddressing = true`, since only 32-bit-clean ROMs are supported going forward; collapse `TwentyFourBitAddressing` to a compile-time `false` and let the dead branches in `Mac2HostAddr`/`is_scc_addr`'s 24-bit mirror ranges (`cpu_emulation.h`) be removed once nothing sets the flag. No alignment-trap work is needed (§2C) — this phase is pure simplification/deletion, not new logic.

**Phase 3 — Shared JIT host-support module.** Extract W^X nesting + icache-flush logic (D) into `BasiliskII/jit_support/`; migrate UAE compemu's ARM64 backend onto it; research whether `cranelift-jit` accepts a custom memory manager on macOS for m68k-rs, or whether the vendored crate needs a small patch.

**Phase 4 — Formalize `CPUEngine` capabilities (E).** Add `mem_strategy`/`tier` to all remaining engines (Musashi, UAE, m68k-rs); surface in test harness output and future prefs UI.

Each phase is independently shippable; Phase 0 alone is a real simplification with no design risk.
